## Project Overview

FMF Dinner Sign-up is a full-stack web app for the FullMetal Falcons robotics team. It manages a rotating dinner schedule where parent households sign up to provide meals at team meetings. Three access tiers: public calendar, parent sign-up (GUID link), and admin management.

## Commands

**Package manager:** Bun

```bash
bun run dev          # Start dev server (hot reload)
bun run build        # Production build
bun run build:dev    # Development build
bun run lint         # ESLint check
bun run format       # Prettier auto-format
```

No test framework is configured.

## Architecture

**Framework:** TanStack Start (Vite-based meta-framework) with React 19, TypeScript, TanStack Router (file-based), TanStack Query. Deploy target: Cloudflare Workers (`src/server.ts`).

**Database:** Supabase (PostgreSQL). Schema lives in `supabase/migrations/`. Two Supabase clients:

- `src/integrations/supabase/client.ts` — browser client (anon key, localStorage session)
- `src/integrations/supabase/client.server.ts` — server-side admin client (service role key, bypasses RLS)

**Server Functions:** All backend logic is in `src/lib/*.functions.ts` using TanStack Start's `createServerFn()` pattern. These become automatic HTTP endpoints. Admin operations check auth in each function using `requireAdmin()` from `src/lib/dinners.server.ts`.

**Routes (`src/routes/`):**

- `index.tsx` — Public calendar; reads `v_meeting_status` view
- `parent.$guid.tsx` — Parent sign-up page; GUID validated server-side via `getParentByGuid()`
- `admin.tsx` — Admin shell layout (checks Supabase auth + `user_roles` table)
- `admin.*.tsx` — Admin sub-pages (meetings, students, buyouts, overview, settings, emails, invites)
- `routeTree.gen.ts` — Auto-generated by TanStack Router; do not edit

**Authentication flow:**

1. Public → no auth
2. Parents → unique GUID embedded in emailed link → validated per-request server-side
3. Admins → Supabase Auth (email/password or Google OAuth) + `user_roles` table with `role='admin'`; first authenticated user auto-claims admin via bootstrap logic

**Email:** Sent via Resend through a Lovable connector gateway. Templates stored in the `email_templates` DB table and rendered with `{{variable}}` interpolation in `src/lib/email.server.ts`.

## Key Database Objects

Tables: `settings`, `students`, `parents`, `meetings`, `sign_ups`, `buy_outs`, `user_roles`, `email_templates`

Important views/functions:

- `v_meeting_status` — Public aggregated view (meeting date + which household signed up)
- `household_progress()` — Supabase RPC; calculates dinners required vs. fulfilled per household
- `has_role()` — Security-definer function used in RLS policies

RLS: Public read on `settings`, `meetings`, `students`. Admin full-access via `has_role()`. Parents and sign-ups bypass RLS through the server-side admin client.

## Environment Variables

`.env` (client + build-time):

- `SUPABASE_URL`
- `SUPABASE_PUBLISHABLE_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY`
- `VITE_SUPABASE_PROJECT_ID`

Server-only (set in hosting environment, not `.env`):

- `SUPABASE_SERVICE_ROLE_KEY` — admin DB access
- `RESEND_API_KEY` — email sending
- `LOVABLE_API_KEY` — Lovable connector gateway auth

## UI

Tailwind CSS v4 + shadcn/ui (new-york style, Lucide icons). Design tokens use oklch color space defined in `src/styles.css`. Component primitives are in `src/components/ui/` (auto-generated via shadcn CLI; don't hand-edit unless fixing a bug).
